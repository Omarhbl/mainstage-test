# Mainstage security review — 16 November 2026

Scope: non-destructive HTTPS checks of www.themainstagent.com, local application source review, and npm production dependency audit. No credentials were changed, private client records accessed, valid forms submitted, or exploitation/load testing performed. Local source includes unfinished app features and is not identical to the deployed build. This is a focused review, not a security certification or evidence of compromise.

## Priority findings

### 1. High — client portal trusts user-editable authorization metadata

Evidence: `src/lib/supabase/client-portal.ts:34` chooses the client using `user.user_metadata.client_slug` before the server-stored `authUserId` relationship. `src/app/backstage/login/actions.ts` repeats this logic. The client object is loaded with a service-role-backed helper, and portal actions use this authorization result when writing messages/projects.

Impact: a signed-in account able to update its own Supabase metadata can potentially claim another client slug and access or modify that client's portal. Supabase documents that user metadata is user-editable and must not be trusted for authorization. This path was confirmed by code inspection; no account or client data was used to exercise it live.

Fix first: resolve the account exclusively through the server-controlled `authUserId === user.id` mapping; deny absent mappings. Apply the same rule to login, all portal pages, and actions. Test two separate client accounts and an unassigned account.

Reference: https://supabase.com/docs/guides/database/postgres/row-level-security

### 2. High priority — vulnerable dependency versions

`npm audit --omit=dev --json` reports eight affected packages: one critical, five high, two moderate. These are package-level classifications, not eight confirmed exploitable website flaws.

The repository pins Next.js 16.2.2. At least one applicable advisory covers App Router applications with Server Actions, which this application uses: GHSA-m99w-x7hq-7vfj (denial of service). Other advisories have platform/feature conditions and require individual triage; the critical aggregate does not establish remote code execution on this Vercel deployment.

Do not use `npm audit fix --force` blindly. The current node_modules directory is a symlink to another checkout, so installing here would also change that checkout.

### 3. Medium — article HTML sanitizer permits unsafe URL schemes

Evidence: `src/lib/article-rich-text.ts:106` escapes attribute text without validating URL protocols. A local inert test confirmed that a javascript URL containing an embedded tab remains in an anchor href after sanitization. Browsers normalize such URL whitespace. Rich content is rendered using `dangerouslySetInnerHTML`.

Impact: malicious or compromised editorial access could publish a script-bearing link that executes when clicked. This is not an anonymous article-write vulnerability. No payload was published or executed in a visitor browser.

Fix: use a maintained parser-based HTML sanitizer with explicit allowed protocols for href/src, and regression tests for obfuscated schemes, malformed HTML and normal editorial content. Add a carefully tested Content Security Policy as defense in depth.

### 4. Medium — public submission abuse and oversized fields

Evidence: contact and guestlist handlers accept JSON with no application-level rate limiting, bot verification, explicit body cap or field-length limits. Contact accepts arbitrary-length names, subject and message. Both expose raw exception messages on failure and can fall back to growing JSON arrays in site_settings.

Impact: spam, unnecessary database/external-copy work, larger records and degraded inbox usability. Vercel infrastructure limits still apply; Cloudflare/Vercel custom rules were not inspected, so absence of all edge protection is not established.

Fix: bounded request parsing and field lengths; distributed rate limiting or verified edge rules; bot challenge/honeypot where appropriate; generic public errors; keep submissions in dedicated tables rather than unbounded settings arrays.

### 5. Medium — analytics endpoint has no authorization

Evidence: `src/app/api/analytics/route.ts:3` has no session/role guard. Live unauthenticated GET returned HTTP 500 with `error` and `debug` JSON keys, confirming public debug output. No actual private key was returned in the inspected response. When configured, code returns Google Analytics realtime report data to any caller and can consume upstream quota.

Fix: require an appropriate backoffice role before contacting Google, remove environment/debug details including TEST_ENV, and use private no-store responses.

### 6. Medium — editorial image uploads trust supplied file type

Evidence: `src/app/api/backoffice/article-inline-image/route.ts` and the article image helper upload arbitrary nonempty files using caller-provided MIME type. The inline route does not decode the image or apply an explicit size/type allowlist. These routes require authenticated editorial access. The newer app-image path already has stricter checks.

Impact: authenticated users can store unexpected file types or expensive/malicious image inputs; exact impact also depends on Storage bucket configuration and serving origin. This is not a confirmed unauthenticated upload or main-origin script execution.

Fix: apply byte-level raster image validation, bounded size/pixel count, server-chosen MIME/extension and safe storage paths to all image paths. Verify bucket MIME/size rules independently.

### 7. Medium — spreadsheet formula injection in contact exports

Evidence: `src/app/api/contact/export/route.ts:5` quotes CSV fields but does not neutralize formula prefixes in public-submitted values. Quoting alone does not prevent spreadsheet formula interpretation.

Impact: opening an exported submission in a spreadsheet may interpret attacker-controlled cells as formulas; behavior depends on the spreadsheet and its protections.

Fix: export XLSX with explicit string cell types, or neutralize formula-leading characters (including leading control/whitespace variants) before CSV serialization. Check guestlist exports too.

### 8. Low — missing browser security response headers on production

Live homepage has HSTS but lacks X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Content-Security-Policy. The first three are already added locally in next.config.ts, but are not deployed yet. Absence alone does not prove exploitation.

Deploy and verify nosniff, SAMEORIGIN and strict-origin-when-cross-origin. Develop a compatible CSP in report-only mode first, considering analytics, embeds, image hosts and Next.js scripts.

## Checks that passed

- HTTPS homepage returns 200 with HSTS.
- Signed-out backoffice, team page and test client-portal URL deliver login redirects with private/no-store caching. Next.js streamed redirects may use HTTP 200; this alone is not a bypass.
- Contact/guestlist exports returned login HTML rather than CSV for unauthenticated requests.
- Cron endpoint rejects requests without its authorization secret (401).
- `/.env` and `/.git/config` return 404.
- Temporary venue preview returns 404 on production. Its local source still exists and must be removed before the next deployment.
- Only `.env.example` is tracked among .env files. A limited signature scan of source/public/scripts/docs found no matching private-key blocks or common token signatures. This is not a full history or deployed-bundle secret scan.
- Backoffice role checks use the profiles table and server-verified auth.getUser(), unlike the client metadata issue.

## Not independently verified

Supabase RLS policies (especially profiles role updates, private submissions and site_settings), Storage policies/bucket settings, open signup settings, MFA, password policy, production firewall/rate limits, backups/restore, logging/incident alerts, dependency provenance, all historical secrets, and multi-user browser isolation. No database policy migrations are present in this checkout. These need direct configuration inspection and controlled test accounts before a stronger security conclusion.

## Recommended sequence

1. Repair client authorization and update affected dependencies.
2. Fix sanitizer, analytics access and upload validation.
3. Protect public forms and CSV exports.
4. Deploy the pending headers, then evaluate CSP.
5. Verify Supabase policies and account protections; retest with admin, editor, client A, client B and anonymous users.

No remediation was deployed during the initial audit. No evidence of a breach was established by these checks.

## Remediation follow-up — 16 November 2026

The follow-up implements server-controlled client account mapping in both login and portal access; parser-based article sanitization; decoded/re-encoded editorial images with 4 MB / 40 MP limits; authenticated private analytics responses; bounded JSON requests and fields, origin checks, shared atomic submission rate limits, generic public errors and bounded legacy inbox growth; spreadsheet-safe CSV; browser response headers with a baseline CSP; and an explicit server-only boundary on the Supabase module.

Next.js is updated to 16.4.6 and sharp to 0.35.5; compatible transitive dependencies are patched. The follow-up production npm audit reports zero known advisories. Seven security regression tests cover forged client metadata, sanitizer bypasses, concurrent rate limits, input bounds, CSV, image decoding and analytics authorization. The isolated security release builds successfully; unrelated unfinished mobile-app changes are excluded.

Direct Supabase inspection found RLS disabled on site_settings and backoffice_articles. The transaction in lock-down-database.sql was applied through the authenticated SQL editor. Verification showed RLS enabled on all three application tables (including profiles), no anon SELECT grant, and no authenticated INSERT/UPDATE/DELETE grants. Restrictive policies reinforce those grants, and profiles retain authenticated own-profile reads. A restrictive Storage policy denies direct client access to media-assets while preserving public image delivery and server uploads. No application records were deleted. Live public content APIs continued to return HTTP 200 afterward.

Important verification correction: the initial local REST count probe used the variable named NEXT_PUBLIC_SUPABASE_ANON_KEY, but later classification found that local value is actually a secret-type key. Its profile count is therefore not evidence of anonymous profile exposure. Follow-up permission conclusions use database role/ACL inspection instead. Fourteen homepage JS bundles were checked for that value and secret-key signatures; no matches were found. Environment key naming should still be cleaned up separately; no key rotation was performed or claimed.

Residual scope: MFA enrollment/enforcement, backups/restore, historical access-log investigation, all environment scopes and full authenticated multi-user browser testing are not certified by this work. The local rate-limit integration and mocked concurrent requests were tested; load testing against production was not performed. Legacy inbox fallbacks now stop accepting new entries at 1,000 rather than silently deleting history; dedicated submission tables remain a future migration.
